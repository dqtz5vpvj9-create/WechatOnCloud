# 手机聊天记录迁移

本功能回应上游 [#121](https://github.com/Gloridust/WechatOnCloud/issues/121)：把微信实例的 TCP 8015 映射保存为实例声明，避免在管理工具里手工添加的映射随着重建而丢失。它提供网络配置和诊断入口，不直接读取、解密或合并微信聊天数据库。

## 证据与边界

2026 年 10 月 14–16 日，issue 作者报告开放实例 TCP 8015，并配置路由或路由器 DNAT 后完成了手机到实例的迁移，同时指出升级/重建会丢失手工映射：[成功报告](https://github.com/Gloridust/WechatOnCloud/issues/121#issuecomment-6169535573)、[路由示例](https://github.com/Gloridust/WechatOnCloud/issues/121#issuecomment-6187975126)、[监听端口检查](https://github.com/Gloridust/WechatOnCloud/issues/121#issuecomment-6193774419)。这是特定环境的用户报告，没有证明所有微信版本和网络环境都适用。

早期讨论把问题归为必须处于同一二层广播域，后续的跨网段成功报告说明这不能作为所有环境的定论。本 fork 采用可验证的 TCP 端口配置，保留 Docker 桥接网络及面板反向代理。

## 面板操作

1. 先使用[本 fork 的面板镜像](fork-build.md)。进入管理页，在微信实例的设置中打开“聊天记录迁移”。
2. 开启映射，填写 **Docker 宿主机实际拥有的局域网 IPv4 地址**；默认宿主端口为 `8015`。容器目标端口固定为 `8015/TCP`。
3. 保存。运行中的实例会短暂重建，保留数据卷及原镜像；停止中的实例只保存配置，下次明确启动时应用。运行时应用失败会尝试恢复之前的配置与原镜像，并显示错误。
4. 在微信内进入聊天记录迁移流程，再点击“检测容器端口”。微信未开始迁移时可能尚未监听 8015，此时检测失败不能直接判定网络故障。
5. 根据下面的网络说明，让手机能够访问微信迁移流程实际使用的地址，再由微信完成迁移。迁移完成后可以关闭映射；关闭映射需要重建运行中的实例，不删除聊天记录。

功能默认关闭，启用时只接受明确的 RFC1918 IPv4（`10/8`、`172.16/12`、`192.168/16`）和 1–65535 的整数端口。不能填写 `0.0.0.0`、回环、公网 IP 或主机名。多个实例必须使用不同的宿主地址/端口组合，例如同一宿主上的 `8015`、`18015`；每个容器内仍用 8015。迁移配置和修改权限仅管理员可用。

面板检查的是**实例内 8015 是否监听，以及面板到实例 8015 的 TCP 连通性**。它不会从手机发包，也不验证宿主端口、路由器规则或聊天记录传输结果。实际映射字段来自 Docker 运行状态，配置声明与运行映射不一致时显示待应用。

## 手机为何仍可能提示不在同一网络

Docker 端口映射会建立“宿主机 IP:宿主端口 → 容器 IP:8015”的入口，**不会修改微信告诉手机的目标 IP**。如果微信让手机连接容器的私有 IP，仅能打开面板或访问宿主机还不够。

以下地址只作为例子：宿主机 `192.168.1.20`、容器 `172.20.1.4`、Docker 网段 `172.20.1.0/24`。应以面板显示的当前容器 IP/网段和宿主的真实地址为准。容器 IP 可能在重建后变化，因此引用单个容器 IP 的外部规则也要核对更新。

### 路由器 DNAT

如果手机连接微信公布的 `172.20.1.4:8015`，可在处理这条流量的路由器上，将该目标改写到 `192.168.1.20:8015`，由 Docker 的已发布端口继续转发。这需要路由器能接收到目标流量，并具备对应的 DNAT 配置能力。

回程也必须经过正确的 NAT 路径；手机和宿主同处一个物理 LAN 时，路由器可能还需要 NAT 回流/SNAT，防止宿主直接向手机回包、绕过路由器的连接状态。具体规则取决于路由器和拓扑，本项目不自动改写路由器或宿主防火墙。

### 直接路由到 Docker 网段

另一条路径是让手机或其网关把 `172.20.1.0/24` 路由到宿主 `192.168.1.20`。这同时要求 Docker 和宿主防火墙允许从该入口转发到容器。

Docker 官方文档明确指出：默认 Linux bridge 禁止远端直接访问容器 IP，只能访问发布在宿主上的端口。当前版本的直接路由需要显式配置，例如受信任宿主接口；**静态路由加上端口发布本身不能保证可达**。参见 [Docker port publishing / direct routing](https://docs.docker.com/engine/network/port-publishing/#direct-routing)。

本功能要求能执行 IPv4 NAT 端口发布的 bridge 网络。`host`、`macvlan`、`routed`、内部隔离网络和关闭 IPv4 的网络不在本次支持范围，开启映射前会拒绝不支持的网络。`routed` 网关模式会忽略宿主端口，见 [Docker gateway modes](https://docs.docker.com/engine/network/port-publishing/#gateway-modes)。本功能不会全局打开 Docker 的 direct-routing。

## 持久化与排查

迁移声明随实例信息保存在面板的 `accounts.json` 中。正常启动、重启、升级和重建使用同一份声明；数据卷保留，应用迁移配置不会隐式更新微信实例镜像。面板自身重启后仍可读回配置；若恰在应用中断电，界面会提示中断和待核实状态，避免把未完成的操作显示为成功。

“停止时只保存”指这次保存请求不会启动容器。上游面板启动时会尝试启动已登记实例；本功能沿用这一行为，因此随后重启面板也可能触发已保存配置的应用。

| 现象 | 先检查什么 |
| --- | --- |
| 无法保存 | 地址是否为宿主实际拥有的私网 IPv4；端口是否与其他实例或 Docker 容器冲突 |
| 保存后恢复旧配置 | 查看应用错误；宿主地址不存在、非 Docker 程序占用端口等可能到 Docker 启动时才被发现 |
| 8015 未监听 | 微信是否已经进入迁移流程；客户端当前版本是否仍使用这个端口 |
| 面板能连，手机不能 | 微信公布的 IP、手机路由、路由器 NAT 回程、宿主转发与防火墙 |
| 容器重建后手机又不通 | 对照面板当前容器 IP，更新按容器 IP 写死的外部规则；确认实际发布映射仍在 |
| 升级后看不到本功能 | 实际部署是否仍在使用上游面板镜像，参见 fork 构建说明 |

例如在手机同一网络的电脑上测试 **微信实际使用的目标地址** 的 TCP 8015，能比 `ping` 更直接定位迁移通路。保持微信迁移页面开启再测试；一次 TCP 成功仍不代表微信协议握手或数据传输已成功。

现有数据卷备份/恢复适合备份整个 Linux 实例。它不承诺把 Windows/macOS 的微信目录直接覆盖到 Linux 后能被读取，跨客户端的数据格式兼容需要由微信支持的迁移流程验证。

## 开发验证

安装前后端依赖后，可运行 `npm run check --prefix panel/server`、`npm test --prefix panel/server`、`npm run check --prefix panel/web` 和 `npm test --prefix panel/web`。后端 HTTP 测试使用真实 Fastify 和登录会话，Docker 指向不存在的临时 socket；它验证访问控制和写入前校验。

在原生 Linux Docker 主机上，还可构建面板并运行实际网络/生命周期回归：

```bash
docker build --provenance=false --sbom=false -t woc-panel-migration:test panel
python3 scripts/test-migration-docker.py
```

脚本创建独立面板、网络、卷和监听 8015 的 Node 测试程序，检查映射持久化、停止保存、原镜像保留、真实宿主端口冲突回滚、明确升级和关闭映射，并精确清理自己的资源。它需要本机 Docker socket 和可绑定的 RFC1918 IPv4，不能在没有本机 Docker 网络的普通 Docker Desktop 客户端直接运行。

这些测试由 `verify-migration` 工作流执行。测试程序没有登录微信，所有检查通过也不等于已完成手机到微信的聊天记录迁移；最终还需在目标设备和网络中验收。
